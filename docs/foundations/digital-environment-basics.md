# مبانی محیط‌های دیجیتال

## سند پایه برای Melakat

**نسخه:** Digital Environment Foundation v0.1  
**وضعیت:** مطالعه و specification پیش از implementation  
**هدف:** فهم دقیق داده، بیت، حافظه، محاسبه، برنامه، اجرا، کپی، سخت‌افزار، نرم‌افزار و ماشین مجازی

## 1. چرا این سند لازم است؟

پیش از ساختن شبیه‌سازی حیات دیجیتال، باید بدانیم «محیط دیجیتال» دقیقاً چیست. اگر محیط را مبهم تعریف کنیم، بعداً ممکن است این مفاهیم را اشتباه بگیریم:

- حافظه‌ی واقعی کامپیوتر با حافظه‌ی جهان شبیه‌سازی؛
- کپی‌کردن یک آرایه با خودتکثیری یک موجود؛
- اجرای یک instruction با اجرای کد واقعی سیستم‌عامل؛
- محدودیت یک VM با محدودیت Python؛
- داده با برنامه؛
- زمان واقعی کامپیوتر با زمان جهان دیجیتال؛
- انرژی فیزیکی سخت‌افزار با energy انتزاعی مدل.

هدف این سند شبیه‌سازی ترانزیستورها نیست. هدف، ساختن یک مدل روشن و قابل‌ممیزی از قوانینی است که درون آن موجودات دیجیتال زندگی می‌کنند.

## 2. پاسخ کوتاه: آیا جهان دیجیتال حافظه و محاسبه دارد؟

بله؛ اما باید میان سه معنای مختلفِ «جهان دیجیتال» تفاوت بگذاریم:

1. سخت‌افزار فیزیکی، مانند تراشه، حافظه‌ی RAM، پردازنده و مدارهای الکترونیکی؛
2. نرم‌افزار، مانند سیستم‌عامل، compiler، interpreter و برنامه؛
3. محیط مجازی، مانند یک VM که برای برنامه‌ها حافظه، دستور، زمان و قوانین جداگانه تعریف می‌کند.

در همه‌ی این سطوح، حالت‌هایی وجود دارد که می‌توانند با قانون‌های مشخص تغییر کنند. در سخت‌افزار، این حالت‌ها به مدار و ولتاژ وابسته‌اند. در نرم‌افزار، با داده و دستور توصیف می‌شوند. در VM، آن‌ها بخشی از specification محیط هستند.

برای Melakat، مهم‌ترین نکته این است:

> ما قرار نیست کل سخت‌افزار واقعی را شبیه‌سازی کنیم؛ ما یک محیط مجازی محدود می‌سازیم که روی سخت‌افزار واقعی اجرا می‌شود.

## 3. چهار لایه‌ی محیط دیجیتال

~~~mermaid
flowchart TD
    H["L0: Physical hardware"]
    S["L1: Host software"]
    V["L2: Melakat VM and digital physics"]
    O["L3: Digital organisms"]
    H --> S --> V --> O
~~~

### L0 — سخت‌افزار فیزیکی

این لایه شامل ترانزیستور، مدار منطقی، پردازنده، حافظه، گذرگاه، دستگاه ذخیره‌سازی، سیستم خنک‌کننده و منابع توان است. محاسبات در این لایه در نهایت فرایندهای فیزیکی‌اند.

### L1 — نرم‌افزار میزبان

سیستم‌عامل و runtime، منابع سخت‌افزار را مدیریت می‌کنند. شبیه‌ساز Python نیز در این لایه یا بالای آن اجرا می‌شود. این لایه فایل، شبکه، پردازه، clock واقعی و ورودی‌خروجی را کنترل می‌کند.

### L2 — ماشین مجازی Melakat

این لایه محیط مصنوعی ماست. در آن باید به‌صورت صریح تعریف کنیم:

- چه نوع حافظه‌ای وجود دارد؛
- چه دستورهایی مجازند؛
- هر instruction چه اثری دارد؛
- زمان چگونه جلو می‌رود؛
- منابع چقدرند؛
- خطا چگونه رخ می‌دهد؛
- موجود چگونه متوقف، تکثیر یا حذف می‌شود.

### L3 — موجود دیجیتال

موجود دیجیتال یک برنامه‌ی Python آزاد نیست. این موجود، داده‌ای است که در قالب یک genome ذخیره شده و همراه با state، memory، instruction pointer و resource budget درون VM تفسیر می‌شود.

## 4. دیجیتال‌بودن در سخت‌افزار یعنی چه؟

### 4.1 بیت

bit کوتاه‌شده‌ی binary digit است و دو مقدار منطقی دارد:

~~~text
0 یا 1
~~~

طبق تعریف NIST، bit یک رقم دودویی با مقدار صفر یا یک است. این دو مقدار معمولاً با بازه‌هایی از وضعیت فیزیکی، مانند سطح ولتاژ، نمایش داده می‌شوند؛ خودِ صفر و یک، برچسب انتزاعی ما برای دسته‌بندی آن وضعیت‌ها هستند.

منبع:

- [NIST: bit](https://csrc.nist.gov/glossary/term/bit)

### 4.2 بایت

یک byte در تعریف رایج شامل هشت bit است:

~~~text
1 byte = 8 bits
~~~

پس یک byte می‌تواند 256 الگوی متفاوت داشته باشد:

~~~text
00000000 تا 11111111
~~~

این الگوها ذاتاً عدد، متن یا instruction نیستند. معنا به قرارداد تفسیر وابسته است.

منبع:

- [NIST: byte](https://csrc.nist.gov/glossary/term/byte)

### 4.3 داده معنا را از خودش ندارد

همین هشت bit می‌تواند بر اساس قرارداد، یکی از این‌ها باشد:

- عدد unsigned؛
- عدد signed؛
- بخشی از یک عدد بزرگ‌تر؛
- یک حرف در encoding؛
- opcode؛
- آدرس حافظه؛
- رنگ یا نمونه‌ی صوتی؛
- بخشی از genome.

بنابراین «داده» و «دستور» گاهی از نظر شکل فیزیکی یکسان‌اند؛ تفاوت آن‌ها از نحوه‌ی تفسیر می‌آید.

این نکته برای Melakat بسیار مهم است: genome باید داده‌ی خامِ درون جهان باشد و فقط VM تعیین کند که هر موقعیت چگونه تفسیر می‌شود.

## 5. عدد و محاسبه در محیط دیجیتال

### 5.1 دامنه‌ی محدود

با n bit، حداکثر 2^n الگوی متفاوت داریم. بنابراین نمایش دیجیتال همیشه دامنه‌ی محدود یا قراردادی دارد.

برای مثال، اگر یک مقدار unsigned هشت‌بیتی داشته باشیم:

~~~text
0 تا 255
~~~

اگر حاصل محاسبه از این دامنه بیرون برود، VM باید رفتار مشخصی داشته باشد:

- overflow و برگشت دورانی؛
- توقف با خطا؛
- اشباع در کمینه یا بیشینه؛
- یا افزایش اندازه‌ی مقدار، اگر specification اجازه دهد.

نباید از integerهای بی‌نهایت بزرگ Python استفاده کنیم و بعد وانمود کنیم جهان دیجیتال ما حافظه و دامنه‌ی نامحدود دارد.

### 5.2 عدد صحیح و اعشاری

integer معمولاً مقدار گسسته و محدود دارد. floating point برای تقریب عددهای حقیقی استفاده می‌شود و خطای گردکردن و دامنه‌ی محدود دارد.

برای نسخه‌ی اولیه‌ی Melakat، استفاده از عددهای صحیح محدود ساده‌تر و قابل‌آزمون‌تر است. اگر بعداً floating point لازم شد، باید precision، rounding، NaN، infinity و هزینه‌ی آن جداگانه تعریف شوند.

### 5.3 محاسبه فقط جمع نیست

یک ALU یا واحد محاسبه و منطق می‌تواند عملیات‌هایی مانند این‌ها را انجام دهد:

- جمع و تفریق؛
- مقایسه؛
- AND، OR و XOR؛
- جابه‌جایی bitها؛
- پرش و انتخاب مسیر.

ترکیب همین عملیات پایه می‌تواند منطق برنامه‌های پیچیده‌تر را بسازد. اما هر primitive اضافه، فضای رفتاری و امکان ظهور الگوهای جدید را تغییر می‌دهد؛ بنابراین instruction set باید کمینه و توجیه‌پذیر باشد.

## 6. سخت‌افزار واقعی چگونه محدودیت ایجاد می‌کند؟

دوره‌ی آموزشی Computation Structures در MIT مسیر ساخت یک سیستم دیجیتال را از ترانزیستور و logic gate تا مدارهای ترکیبی، مدارهای ترتیبی، ماشین حالت، پردازنده و سیستم کامل توضیح می‌دهد. این مسیر نشان می‌دهد که abstractionهای نرم‌افزاری روی لایه‌های سخت‌افزاری ساخته می‌شوند، نه اینکه جدا از آن‌ها وجود داشته باشند.

منبع:

- [MIT OpenCourseWare: Computation Structures](https://ocw.mit.edu/courses/6-004-computation-structures-spring-2017/)

### اجزای اصلی

#### Transistor و logic gate

ترانزیستور می‌تواند در مدار به‌عنوان یک عنصر کنترل‌کننده‌ی جریان عمل کند. ترکیب ترانزیستورها، gateهایی مانند NOT، AND و OR را می‌سازد. gateها عملیات منطقی روی وضعیت‌های دیجیتال را ایجاد می‌کنند.

#### مدارهای combinational

خروجی این مدارها تابعی از ورودی فعلی است. نمونه‌ی آن بخشی از ALU است.

#### مدارهای sequential

خروجی آن‌ها به ورودی و state قبلی وابسته است. register و حافظه از این ایده استفاده می‌کنند.

#### Clock

بسیاری از سیستم‌ها تغییر state را با سیگنال clock هماهنگ می‌کنند. clock فیزیکی با tick جهان Melakat یکی نیست، اما به ما یادآوری می‌کند که ترتیب و زمان‌بندی انتقال state باید تعریف شود.

#### CPU

پردازنده دستورها را می‌خواند، تفسیر می‌کند و عملیات لازم را روی registerها و حافظه انجام می‌دهد.

#### RAM

حافظه‌ای سریع برای نگهداری موقت دستورها و داده‌های فعال است. ظرفیت آن محدود و دسترسی به آن زمان‌مند است.

#### Storage

ذخیره‌سازی پایدار مانند SSD یا دیسک برای نگهداری داده در زمان طولانی‌تر استفاده می‌شود. storage با RAM یکی نیست.

#### Bus و I/O

گذرگاه‌ها و رابط‌های ورودی‌خروجی ارتباط میان CPU، حافظه و دستگاه‌ها را ممکن می‌کنند. در Melakat این مسیرها نباید به‌طور ضمنی در اختیار genome قرار بگیرند.

MIT در توضیح ساختار سیستم، CPU و main memory را هسته‌ی engine محاسباتی، و storage، timer، دستگاه‌ها و network را اجزای پیرامونی توصیف می‌کند.

منبع:

- [MIT OpenCourseWare: system organization and lecture notes](https://ocw.mit.edu/courses/6-004-computation-structures-spring-2009/pages/lecture-notes/)

### محدودیت‌های مهم سخت‌افزار

- ظرفیت محدود حافظه؛
- تعداد محدود registerها؛
- اندازه‌ی محدود word؛
- سرعت محدود clock؛
- latency در حافظه و دستگاه‌ها؛
- پهنای باند محدود؛
- مصرف توان و تولید گرما؛
- محدودیت موازی‌سازی و synchronization؛
- خطا، نویز و خرابی فیزیکی؛
- دقت محدود نمایش عدد.

این محدودیت‌ها مستقیم یا غیرمستقیم روی نرم‌افزار اثر می‌گذارند. مثلاً برنامه نمی‌تواند واقعاً از حافظه‌ای بیشتر از ظرفیت سخت‌افزار استفاده کند؛ سیستم‌عامل ممکن است با virtual memory ظاهری بزرگ‌تر بسازد، اما هزینه و محدودیت فیزیکی حذف نمی‌شود.

## 7. نرم‌افزار چیست؟

نرم‌افزار مجموعه‌ای از دستورها، داده‌ها و قراردادهای تفسیر است که روی سخت‌افزار اجرا می‌شود. چند سطح مهم را باید جدا کنیم:

### Firmware

نرم‌افزار نزدیک به سخت‌افزار که هنگام راه‌اندازی یا کنترل یک دستگاه اجرا می‌شود.

### Operating system

سیستم‌عامل منابعی مانند CPU، memory، storage، فایل، دستگاه و network را مدیریت می‌کند و به برنامه‌ها interface می‌دهد.

### Compiler

compiler یک زبان یا نمایش ورودی را به نمایش دیگری، معمولاً instructionهای سطح پایین‌تر، تبدیل می‌کند.

### Interpreter

interpreter معمولاً دستور یا ساختار ورودی را در زمان اجرا می‌خواند و semantics آن را اعمال می‌کند.

### Runtime

runtime محیطی است که اجرای برنامه را پشتیبانی می‌کند؛ ممکن است حافظه، garbage collection، کتابخانه و خدمات دیگر فراهم کند.

### Program

program یک توصیف ایستا از دستورها و داده‌هاست.

### Process

process یک نمونه‌ی در حال اجرای program است و علاوه بر دستورها، state مخصوص خود را دارد:

- registerها؛
- program counter؛
- stack؛
- memory؛
- منابع؛
- وضعیت اجرا.

دو process می‌توانند از یک program یکسان ساخته شوند، اما state و سرنوشت متفاوت داشته باشند.

## 8. چرخه‌ی اجرای برنامه

مدل کلاسیک اجرای پردازنده را می‌توان به‌صورت زیر خلاصه کرد:

~~~text
fetch
decode
execute
update state
advance or change program counter
~~~

### Fetch

دستور از آدرسی که program counter یا instruction pointer نشان می‌دهد خوانده می‌شود.

### Decode

بیت‌ها یا نمادهای دستور به opcode و operandها تفسیر می‌شوند.

### Execute

عملیات دستور روی register، حافظه یا state اعمال می‌شود.

### Update

program counter، flagها، منابع و وضعیت اجرای process به‌روزرسانی می‌شوند.

مدل ساده:

~~~text
while process.is_running:
    instruction = memory[program_counter]
    operation = decode(instruction)
    state = execute(operation, state)
    program_counter = next_program_counter(state)
~~~

این pseudocode هنوز ناقص است. یک specification واقعی باید رفتار پرش، خطا، دسترسی نامعتبر، حلقه‌ی بی‌نهایت، توقف، مصرف منابع و دسترسی به ورودی‌خروجی را هم تعریف کند.

در MIT، program counter آدرس دستور بعدی را نگه می‌دارد و CPU از instructionها و داده‌های موجود در memory استفاده می‌کند. این مفهوم برای طراحی state ماشین مجازی Melakat مستقیم و ضروری است.

منبع:

- [MIT OpenCourseWare: instruction set and program counter](https://live.ocw.mit.edu/courses/6-004-computation-structures-spring-2017/pages/c10/c10s1/)

## 9. ماشین مجازی چیست؟

Virtual Machine یا VM محیطی است که یک interface محاسباتیِ تعریف‌شده را به program ارائه می‌دهد، بدون اینکه program مستقیماً به تمام جزئیات سخت‌افزار میزبان دسترسی داشته باشد.

یک VM می‌تواند این اجزا را داشته باشد:

- instruction set؛
- registerها؛
- program counter؛
- memory مجازی؛
- stack؛
- ورودی‌خروجی تعریف‌شده؛
- scheduler؛
- trap و error؛
- محدودیت زمانی و حافظه.

### تفاوت VM با شبیه‌ساز سخت‌افزار

یک شبیه‌ساز سخت‌افزار ممکن است تلاش کند رفتار پردازنده‌ی خاصی را با دقت زیاد تقلید کند. اما VM پروژه‌ی Melakat قرار نیست CPU واقعی خاصی را کپی کند. ما یک ماشین مصنوعی و کوچک طراحی می‌کنیم که قوانینش برای سؤال پژوهشی ما مناسب و قابل‌ممیزی باشند.

### تفاوت VM با سیستم‌عامل

سیستم‌عامل محیط عمومی‌تری با فایل، پردازه، device و network است. VM Melakat باید برعکس، محیطی کمینه و بسته باشد. هر قابلیتی که در interface آن تعریف نشود، برای موجود دیجیتال وجود ندارد.

### نمونه‌ی WebAssembly

استاندارد WebAssembly نشان می‌دهد که یک format سطح پایین می‌تواند semantics امن، قابل‌حمل و sandbox‌شده داشته باشد. مشخصات آن core execution را از embedding جدا می‌کند و مدل امنیتی آن module را در محیطی جدا از host اجرا می‌کند. با این حال، capabilityها می‌توانند از طریق importهای محیط میزبان اضافه شوند؛ بنابراین حتی WebAssembly هم بدون تعریف دقیق embedding «خودبه‌خود» کاملاً ایزوله نیست.

برای Melakat، از این منبع فقط درس‌های architecture و isolation را می‌گیریم؛ موجودات را به Web API، فایل، network یا import میزبان وصل نمی‌کنیم.

منابع:

- [W3C: WebAssembly Core Specification](https://www.w3.org/TR/wasm-core/)
- [WebAssembly: Security](https://webassembly.org/docs/security/)

## 10. حافظه چگونه کار می‌کند؟

### 10.1 حافظه‌ی آدرس‌پذیر

حافظه معمولاً مجموعه‌ای از خانه‌هاست که هرکدام آدرس دارند. برنامه با آدرس یا index مشخص می‌کند از کجا بخواند یا کجا بنویسد.

~~~text
address 0  → memory cell
address 1  → memory cell
address 2  → memory cell
...
~~~

در یک سیستم واقعی، همه‌ی آدرس‌ها معتبر نیستند. محدوده‌ی حافظه، permission و mapping تعیین می‌کنند که دسترسی ممکن است یا نه.

### 10.2 Register، stack و heap

- register: حافظه‌ی بسیار کوچک و سریع داخل CPU؛
- stack: ساختار منظم برای call، local state و return؛
- heap: ناحیه‌ای برای تخصیص پویای داده؛
- memory map: قراردادی برای اینکه هر ناحیه چه معنایی دارد.

Melakat لازم نیست همه‌ی این ساختارها را از ابتدا داشته باشد. اما باید صریحاً مشخص کند که کدام state در genome، کدام state در register و کدام state در memory نگهداری می‌شود.

### 10.3 حافظه محدود است

اگر ظرفیت VM برابر N خانه باشد، موجود نمی‌تواند در عمل خانه‌ی N+1 را بخواند یا بنویسد. باید یکی از این رخدادها تعریف شود:

- trap؛
- توقف process؛
- ردشدن عملیات؛
- مرگ موجود؛
- یا رفتار دیگری که specification از قبل تعیین کرده است.

رفتار «هرچه لازم شد memory بیشتری بساز» در جهان محدود ما مجاز نیست.

## 11. تفاوت assignment، copy، clone و replication

این یکی از مهم‌ترین بخش‌های پروژه است.

### 11.1 Assignment یا binding

در بسیاری از زبان‌های سطح بالا، assignment داده را کپی نمی‌کند؛ فقط یک نام یا reference را به همان object متصل می‌کند.

در Python:

~~~text
b = a
~~~

ممکن است a و b به یک object قابل‌تغییر اشاره کنند. تغییر یکی می‌تواند دیگری را هم تغییر دهد.

### 11.2 Shallow copy

یک container جدید می‌سازد، اما ممکن است عناصر داخلی همان referenceهای قبلی باشند.

### 11.3 Deep copy

ساختار را به‌صورت بازگشتی کپی می‌کند تا objectهای داخلی نیز جدا شوند؛ البته رفتار دقیق آن به نوع object و قرارداد زبان وابسته است.

منبع رسمی Python این تفاوت را صریحاً توضیح می‌دهد:

- [Python documentation: copy](https://docs.python.org/3/library/copy.html)

### 11.4 Snapshot

snapshot تصویری از state در یک لحظه است. snapshot برای replay، debugging و restore مفید است؛ اما خودش موجود جدیدی نیست، مگر اینکه طبق قانون از آن process تازه ساخته شود.

### 11.5 Clone

clone معمولاً به ساخت نمونه‌ای از یک state یا object اشاره دارد. clone می‌تواند کاملاً یکسان باشد، اما هنوز نشان نمی‌دهد که موجود اصلی فرایند تکثیر را انجام داده است.

### 11.6 Digital replication

برای Melakat، replication باید یک فرایند درون‌جهانی باشد:

1. موجود منابع لازم را فراهم می‌کند؛
2. genome را از مسیر instructionهای مجاز می‌خواند یا کپی می‌کند؛
3. برای فرزند memory تخصیص داده می‌شود؛
4. دستورها به فرزند منتقل می‌شوند؛
5. mutation ممکن است در مسیر کپی رخ دهد؛
6. state مستقل فرزند ساخته می‌شود؛
7. فرزند طبق قانون وارد جمعیت می‌شود.

کپی‌کردن ساده‌ی یک Python list از بیرون، replication محسوب نمی‌شود.

### جدول تفاوت

| فرایند | چه چیزی را تغییر می‌دهد؟ | آیا اجرای genome لازم است؟ | آیا فرزند مستقل است؟ | کاربرد در Melakat |
|---|---|---:|---:|---|
| assignment | فقط binding یا reference | خیر | معمولاً خیر | برای organism ممنوع یا کنترل‌شده |
| shallow copy | container بیرونی | خیر | شاید خیر | برای state مناسب نیست |
| deep copy | ساختار object | خیر | اغلب بله | فقط برای infrastructure میزبان |
| snapshot | تصویر یک state | خیر | تا زمان restore نامشخص | replay و debugging |
| clone | نمونه‌ی جدید از state | خیر | طبق قرارداد | control experiment |
| replication | genome و body جدید در جهان | بله یا طبق semantics | باید بله باشد | فرایند اصلی تکثیر |

## 12. کپی در Melakat باید چگونه مدل شود؟

در نسخه‌ی صفر، بهتر است این موارد از هم جدا باشند:

~~~text
source_genome
source_state
child_memory
copy_operation
mutation_operation
division_commit
lineage_record
~~~

یک مدل مفهومی:

~~~text
replicate(parent):
    check parent is active
    check energy budget
    allocate child memory
    copy genome instruction by instruction
    apply allowed mutation rule
    create independent child state
    register parent-child lineage
    commit child into population
~~~

### اصل استقلال حافظه

پس از division:

- تغییر در genome فرزند نباید genome والد را تغییر دهد؛
- تغییر در register فرزند نباید register والد را تغییر دهد؛
- حافظه‌ی اختصاصی آن‌ها نباید reference مشترک پنهان داشته باشد؛
- اگر memory مشترک مجاز است، shared بودن آن باید قانون صریح جهان باشد.

### کپی اتمیک یا نیمه‌کاره؟

این یک تصمیم طراحی است. دو گزینه داریم:

- replication اتمیک: یا کل فرایند موفق می‌شود یا هیچ فرزندی ساخته نمی‌شود؛
- replication تدریجی: فرایند می‌تواند نیمه‌کاره بماند و موجود در میانه‌ی آن بمیرد.

برای V0، replication اتمیک برای debugging ساده‌تر است؛ اما اگر بعداً بخواهیم هزینه‌ی واقعی‌تر و شکست در میانه‌ی تولیدمثل را مطالعه کنیم، replication تدریجی می‌تواند در فاز جدا اضافه شود.

## 13. برنامه، داده و کد اجرایی

در دنیای واقعی، یک فایل یا آرایه می‌تواند به‌عنوان داده یا کد تفسیر شود. خطر زمانی ایجاد می‌شود که داده‌ی غیرقابل‌اعتماد بدون کنترل به native execution یا runtime میزبان سپرده شود.

در Melakat:

- genome فقط data است؛
- VM فقط opcodeهای مجاز را می‌شناسد؛
- هیچ genome مستقیماً با Python exec یا eval اجرا نمی‌شود؛
- هیچ genome نمی‌تواند module import کند؛
- هیچ genome به file، network، subprocess، host memory یا API دسترسی ندارد؛
- هر instruction باید در interpreter معنای محدود و ثبت‌شده داشته باشد.

این محدودیت هم برای امنیت لازم است و هم برای علم. اگر موجود بتواند از محیط شبیه‌سازی بیرون برود، دیگر نمی‌دانیم نتیجه از قوانین جهان آمده یا از توانایی‌های سیستم‌عامل.

## 14. زمان، scheduler و اجرا

### 14.1 زمان میزبان و زمان جهان

زمانی که Python روی CPU اجرا می‌شود با زمان tick جهان یکی نیست. ممکن است یک اجرای شبیه‌سازی روی کامپیوتر سریع‌تر یا کندتر شود، اما اگر semantics ثابت باشد، نتیجه‌ی جهان نباید با wall-clock تغییر کند.

### 14.2 Scheduler

اگر چند organism داریم، باید ترتیب اجرای آن‌ها مشخص باشد:

- ترتیبی و ثابت؛
- چرخشی؛
- تصادفی با seed؛
- موازی با قواعد هم‌زمانی.

برای نسخه‌ی اولیه، اجرای ترتیبی و ثبت‌شده کم‌ریسک‌تر است؛ چون اثر رقابت میان ترتیب‌های مختلف را وارد نمی‌کند.

### 14.3 Instruction budget

یک حلقه‌ی بی‌نهایت نباید کل شبیه‌ساز را متوقف کند. پس هر process یا organism باید در هر tick بودجه‌ی مشخصی برای تعداد instruction داشته باشد.

اگر بودجه تمام شود:

- اجرای آن organism برای آن tick متوقف می‌شود؛
- state حفظ می‌شود؛
- هزینه‌ی مشخص اعمال می‌شود؛
- در tick بعد طبق scheduler ادامه می‌دهد؛
- یا طبق قانون دیگری متوقف می‌شود.

این رفتار باید پیش از implementation تصمیم‌گیری شود.

## 15. تصادفی‌بودن و بازتولیدپذیری

تصادفی‌بودن در کامپیوتر معمولاً از یک generator و state داخلی آن می‌آید. برای پژوهش، «تصادفی» نباید به معنی «غیرقابل‌ردیابی» باشد.

هر run باید این موارد را ثبت کند:

- seed؛
- نسخه‌ی VM؛
- نسخه‌ی instruction set؛
- پیکربندی منابع؛
- ترتیب scheduler؛
- genome اولیه؛
- رخدادهای mutation؛
- خروجی نهایی.

با همان seed و همان نسخه‌ی قوانین، اجرای deterministic باید همان نتیجه را تولید کند. اگر parallelism یا زمان‌بندی نتیجه را تغییر می‌دهد، این موضوع باید بخشی از گزارش باشد.

## 16. رابطه‌ی محدودیت‌های سخت‌افزار، نرم‌افزار و VM

سه سطح ظرفیت را جدا کنیم:

| سطح | منبع | محدودیت واقعی |
|---|---|---|
| host hardware | CPU، RAM، storage، توان و زمان | محدودیت فیزیکی کامپیوتر |
| host software | Python، OS، runtime و process limit | محدودیت پیاده‌سازی و دسترسی |
| Melakat VM | virtual memory، instruction budget و world resources | قوانین مصنوعی جهان |

VM نمی‌تواند از host hardware بیشتر از چیزی که واقعاً در دسترس است استفاده کند. از طرف دیگر، Melakat می‌تواند عمداً محدودتر از host باشد؛ مثلاً روی کامپیوتری با RAM زیاد، جهان را با حافظه‌ی مجازی کوچک اجرا کنیم.

برای علم، ظرفیت جهان باید مستقل از سرعت یا مدل کامپیوتر میزبان تا حد امکان ثابت بماند.

## 17. نگاشت لایه‌های واقعی به Melakat

این نگاشت یک analogy عملکردی است، نه ادعای همسانی مادی:

| جهان واقعی یا host | معادل در Melakat | توضیح |
|---|---|---|
| CPU میزبان | engine شبیه‌ساز | قوانین جهان را اجرا می‌کند، اما موجود به آن دسترسی ندارد |
| RAM میزبان | ظرفیت بالادستی implementation | فقط سقف اجرای عملی را تعیین می‌کند |
| OS | خارج از جهان | نباید capability مستقیم برای organism فراهم کند |
| VM memory | حافظه‌ی جهان دیجیتال | محدود، آدرس‌پذیر و نسخه‌پذیر |
| CPU مجازی | execution state هر organism | register، pointer و بودجه‌ی instruction |
| instruction | واحد تغییر state | semantics آن باید ثابت و مستند باشد |
| program counter | instruction pointer | مکان دستور بعدی |
| process | نمونه‌ی فعالِ یک genome | genome به‌علاوه‌ی state و منابع |
| فایل genome | داده‌ی اولیه یا artifact آزمایش | خودِ فایل بیرونی بخشی از جهان نیست |
| scheduler | زمان و ترتیب جهان | اجرای موجودات را تعیین می‌کند |
| random generator | رخدادهای تصادفی مدل | باید seed داشته باشد |
| energy token | منبع انتزاعی جهان | قانون حسابداری، نه انرژی سخت‌افزار |
| memory allocation | رشد یا تشکیل body دیجیتال | باید هزینه و شکست داشته باشد |
| deallocation | مرگ و بازیافت | آزادشدن منابع طبق قانون جهان |

## 18. مدل ریاضی حداقلی محیط دیجیتال

می‌توانیم حالت جهان را به‌صورت یک بردار حالت تعریف کنیم:

~~~text
S_t = {
    world_memory,
    organisms,
    resource_pools,
    scheduler_state,
    random_state,
    metrics
}
~~~

قانون گذار جهان:

~~~text
S_(t+1) = T(S_t, external_input_t, random_event_t)
~~~

در Melakat:

- S_t حالت کامل در tick فعلی است؛
- external_input_t می‌تواند انرژی متوالی ورودی به جهان باشد؛
- random_event_t باید از generator دارای seed بیاید؛
- T تنها جایی است که قوانین جهان را اعمال می‌کند.

این تعریف چند مزیت دارد:

- snapshot کردن ممکن می‌شود؛
- اجرای دوباره قابل‌اعتماد می‌شود؛
- مقایسه‌ی دو نسخه‌ی VM ممکن می‌شود؛
- علت تغییر هر state باید در transition قابل‌ردیابی باشد.

## 19. candidateهای نسخه‌ی صفر

موارد زیر پیشنهاد اولیه‌اند و تا تصویب specification نهایی، قانون قطعی نیستند:

1. genome به‌صورت آرایه‌ای از opcodeهای محدود ذخیره شود؛
2. instructionها در آغاز نمادین و خوانا باشند و encoding باینری بعداً اضافه شود؛
3. arithmetic اولیه فقط با integer محدود انجام شود؛
4. حافظه‌ی جهان finite و addressable باشد؛
5. هر organism memory allocation مشخص داشته باشد؛
6. instruction budget در هر tick وجود داشته باشد؛
7. اجرای organismها sequential باشد؛
8. mutation فقط در مسیر copy و از نوع substitution باشد؛
9. هیچ native execution یا host capability وجود نداشته باشد؛
10. energy به‌عنوان واحد انتزاعی و versioned تعریف شود؛
11. parent و child حافظه‌ی مستقل داشته باشند؛
12. تمام trapها و resource exhaustionها ثبت شوند.

این فهرست هنوز تعیین نمی‌کند که instructionهای دقیق چه باشند یا replication چگونه از رفتارهای اولیه‌ی VM پدیدار شود. آن‌ها باید در Minimal Instruction Set و Reproduction and Mutation Model تصمیم‌گیری شوند.

## 20. چیزهایی که فعلاً شبیه‌سازی نمی‌کنیم

برای جلوگیری از بزرگ‌شدن زودهنگام پروژه، در نسخه‌ی پایه این موارد مدل نمی‌شوند:

- ترانزیستور و مدار الکترونیکی واقعی؛
- ولتاژ، جریان و گرمای واقعی هر gate؛
- معماری خاص یک CPU تجاری؛
- cache و pipeline واقعی host؛
- سیستم‌عامل درون جهان؛
- فایل و شبکه برای organism؛
- compiler زنده برای genome؛
- floating point پیچیده؛
- thread و concurrency آزاد؛
- سیستم‌عامل یا API بیرونی؛
- AI، ML، learning، intelligence یا reward برای complexity.

مدل‌نکردن این موارد به معنی بی‌اهمیت‌بودن آن‌ها نیست. یعنی آن‌ها را عمداً به فازهای بعدی یا خارج از دامنه‌ی پرسش فعلی منتقل می‌کنیم.

## 23. جمع‌بندی

یک جهان دیجیتال فقط مجموعه‌ای از عددها نیست. یک جهان دیجیتال، مجموعه‌ای از stateها، نمایش‌ها، حافظه‌ها، دستورها، قوانین تفسیر، منابع، ترتیب اجرا و مرزهای دسترسی است.

سخت‌افزار واقعی، بستر فیزیکی اجرای محاسبه است. نرم‌افزار، قراردادها و دستورهای قابل‌اجرا را روی این بستر سازمان می‌دهد. VM یک محیط کنترل‌شده و محدود می‌سازد. موجود دیجیتال درون همین محیط، از طریق state و genome خود تغییر می‌کند.

پس برای Melakat، اولین «طبیعت دیجیتال» باید از این اجزای روشن ساخته شود:

~~~text
finite state
+ finite memory
+ limited instruction semantics
+ explicit execution
+ explicit copying
+ explicit mutation
+ bounded resources
+ deterministic scheduler
+ controlled randomness
+ strict sandbox
~~~

تا زمانی که این لایه‌ها دقیق نباشند، هر نتیجه‌ای درباره‌ی تکامل دیجیتال می‌تواند حاصلِ ابهام implementation باشد، نه حاصلِ قوانین جهان.
